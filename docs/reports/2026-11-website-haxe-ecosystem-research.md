# How Haxe and its ecosystem present themselves on the web

Status: research report, 2026-11-23, produced with Codex (web search over the live sites, cited); folded into docs/design/WEBSITE.md ("Coming from Haxe, HashLink and Lime", branding).

Haxe sells compiler breadth. The ecosystem sites make that breadth concrete through games, UI examples, and platform-specific setup guides. Haxeon has a more specific story to show: build a cross-platform app, change its code while it runs, and watch the app keep its state. That interaction should be the first substantial proof on the homepage.

This review covers the six requested sites plus Lime, which explains several of the build and deployment paths that OpenFL and HaxeFlixel rely on. It uses current public pages and linked documentation. Interactive controls and local builds were outside the fetch-based verification. Fetch failures and alternate routes are noted below.

## 1. Site-by-site findings

### Haxe

- **Hero and CTAs.** The headline is “Haxe empowers cross-platform development”. The subheading is “Haxe is an open source high-level strictly-typed programming language with a fast optimizing cross-compiler.” The main CTA is **Download 4.3.7**, dated May 9, 2025. The next block promotes **Download 5.0.0-preview.1**, dated July 4, 2025, and links to nightlies. [Homepage](https://haxe.org/), [Download](https://haxe.org/download/)
- **Homepage order.** Hero and stable download → Haxe 5 preview → compiler targets and execution modes → When Haxe?, Open Source, and Many libraries → Learn Haxe → A taste of Haxe → language and compiler features → news and videos → Foundation, business support, testimonial, and partners. The code appears in a Try Haxe iframe below the learning links. It offers `Game.hx` and `Macro.hx` tabs and **Run** and **Edit** controls. The visible rock-paper-scissors example demonstrates anonymous structures, enums, pattern matching, and `trace`. [Homepage](https://haxe.org/), [Embedded example](https://try.haxe.org/embed/44ddE)
- **Targets and use cases.** The homepage lists JavaScript, C++, C#, Java, JVM, Python, Lua, PHP, and Flash, then separately mentions HashLink, NekoVM, and interpreted execution. The Use Cases section organizes the same cross-platform promise by what people build: games, web, mobile, desktop, command-line tools, and cross-platform APIs. The compiler-target table adds the distinctions a developer needs, including support tier, output kind, and availability of `sys` APIs. [Homepage](https://haxe.org/), [Use Cases](https://haxe.org/use-cases/), [Compiler Targets](https://haxe.org/documentation/introduction/compiler-targets.html)
- **Navigation and adoption proof.** The main navigation has Home, Download, Blog, Use Cases, Haxe Foundation, Support Plans, Learn Haxe, and Connect. **Who Uses Haxe** sits under Use Cases. It presents company logos, including Mattel, Coca-Cola, Hasbro, and Toyota, alongside testimonials and links to ecosystem showcases such as OpenFL, Heaps, and HaxeFlixel. The logos illustrate the breadth of Haxe’s reach. The linked showcases give readers more concrete examples of what was built. [Homepage](https://haxe.org/), [Who Uses Haxe](https://haxe.org/use-cases/who-uses-haxe.html)
- **Getting started and step count.** The homepage leads with Download and offers learning links farther down. The Introduction sends readers to platform-specific setup after downloading Haxe. The JavaScript guide has **six numbered steps**: install Haxe, install a compatible editor, create the project, develop it, compile and run it, and ask the community. The manual’s shorter Hello World takes **two actions after installation**: save `Main.hx` and run `haxe -main Main --interp`. Try Haxe provides a browser route. [Introduction](https://haxe.org/documentation/introduction/), [JavaScript setup](https://haxe.org/documentation/platforms/javascript.html), [Hello World](https://haxe.org/manual/introduction-hello-world.html), [Try Haxe](https://try.haxe.org/)
- **Docs and positioning.** The overall brand is a cross-platform toolkit. The homepage foregrounds the language and optimizing compiler. The API introduction fills out the definition with the shared standard library and access to platform-native capabilities. The Introduction is a map to the language, standard library, compiler, editors, and platform setup. The **Haxe 4 Manual** covers language semantics, macros, compiler behavior, standard library topics, Haxelib, and target details. The versioned **API** is the searchable package/type reference. The community **Cookbook** carries snippets, examples, and tutorials, including a substantial macros category. **Videos** is a separate destination. [Introduction](https://haxe.org/documentation/introduction/), [Manual](https://haxe.org/manual/introduction.html), [API](https://api.haxe.org/), [Cookbook](https://code.haxe.org/), [Videos](https://haxe.org/videos/)

### Haxelib

- **Hero, structure, and CTAs.** The page title is “Haxelib - the Haxe package manager”. The homepage opens directly with **View all Haxelibs**, **Browse by tag**, **Browse by author**, **Recent library updates**, and **Learn Haxelib**. It proceeds through popular tags, recent updates, popular libraries, contributors, and a command example. The featured example uses `actuate` to show installing a library, pinning a version, and passing `-lib` to Haxe. This is a package directory, with release entries and usage examples serving as proof. [Homepage](https://lib.haxe.org/)
- **Getting started and docs.** Haxelib ships with Haxe. The docs show how to install a package and explicitly add it to compilation with `--library` or `-L`. The documentation also covers CLI usage, publishing, per-project setup, adding libraries, and FAQ. [Haxelib documentation](https://lib.haxe.org/documentation)
- **Credible versus dated.** The recent-updates feed showed releases marked today and in the preceding days. Popular downloads and tags such as `flash`, `neko`, `cpp`, and `macro` reveal the ecosystem’s history and dependencies. For a migration decision, a package’s version and tested build matter more than its popularity or tags. The front page listed `hxn-assets`, but its detail page returned a cache miss during this check. [Homepage](https://lib.haxe.org/), [`hxn-assets` listing](https://lib.haxe.org/p/hxn-assets/)

## 2. What Haxe’s positioning gets right and where it asks too much of readers

Haxe addresses developers who want to share source across environments and still reach native APIs. The use-case pages speak to application and game developers, while the Foundation’s support plans, partners, and testimonials also speak to teams evaluating long-term adoption. The ecosystem sites then give those audiences more specific destinations: OpenFL for cross-platform graphics and applications, HaxeFlixel for 2D games, Heaps for 2D and 3D rendering, and HaxeUI for applications across UI backends. [Haxe Use Cases](https://haxe.org/use-cases/), [Haxe Foundation](https://haxe.org/foundation/), [OpenFL](https://www.openfl.org/), [HaxeFlixel](https://haxeflixel.com/), [Heaps](https://heaps.io/), [HaxeUI](https://www.haxeui.org/)

The site does three things well. It names the language and compiler immediately. It gives visitors several kinds of evidence they can inspect, from runnable code and a compiler-target table to a package registry and framework showcases. And it serves different learning needs with a manual, API reference, and task-oriented examples. [Homepage](https://haxe.org/), [Compiler Targets](https://haxe.org/documentation/introduction/compiler-targets.html), [Haxelib](https://lib.haxe.org/), [Cookbook](https://code.haxe.org/)

The cost of breadth is that the reader has to assemble a mental model. The home target list combines output languages, bytecode, runtimes, and interpreted execution. Use Cases describes the things people build, while frameworks determine much of the actual app stack and platform setup. The starter journey branches before a local first run, and the first homepage code example comes after several links and a release promotion. The “Latest news” entries shown on the homepage were from 2020–21, even though the page links to newer compiler releases and Haxelib shows recent package activity. That is a presentation problem and a poor proxy for project activity. [Homepage](https://haxe.org/), [Introduction](https://haxe.org/documentation/introduction/), [Compiler Targets](https://haxe.org/documentation/introduction/compiler-targets.html), [Haxelib](https://lib.haxe.org/)

## 3. What “Coming from Haxe” must answer

A Haxe developer will want to know whether an existing project compiles, which dependencies and build steps carry over, and where the result can run. Haxelib makes installing source packages routine, but the ecosystem also relies on compiler macros, target-specific APIs, build tools, and native libraries. OpenFL depends on Lime for targets, HaxeFlixel layers on OpenFL and Lime, and HaxeUI compatibility depends on the chosen backend. A useful migration guide needs to answer at each of those levels. [Haxelib documentation](https://lib.haxe.org/documentation), [Haxe Manual](https://haxe.org/manual/introduction.html), [OpenFL Targets](https://www.openfl.org/learn/haxelib/docs/targets/), [HaxeFlixel installation](https://haxeflixel.com/documentation/install-haxeflixel/), [HaxeUI backends](https://www.haxeui.org/api/guides/backends.html)

| Reader question | What the page should publish |
| --- | --- |
| **Will my `.hx` source compile?** | A release-specific compatibility table for the growing Haxe subset. Cover syntax, types and semantics, standard library including `sys`, metadata, `#if` defines, target-specific imports, and externs. Show the first error a reader is likely to hit and the corresponding edit. |
| **What happens to macros?** | Give expression, build, and initialization macros explicit statuses. Cover `haxe.macro` APIs and generated sources. Where a feature is unavailable, show a verified workaround or mark the gap. |
| **Can I keep Haxelib and my build files?** | Spell out whether Haxeon consumes packages already installed by `haxelib`, resolves pinned or Git dependencies, or requires dependencies to be added another way. Show what happens to `.hxml`, `-lib`, `-D`, and framework-specific project files or commands. |
| **Which libraries and frameworks work?** | Publish verified package versions and results by JIT, native AOT, and Wasm. Distinguish tested, requires changes, unsupported, and untested. Start with a small pure-Haxe library and give explicit statuses for OpenFL/Lime, HaxeFlixel, Heaps, and HaxeUI by backend. Name blockers such as macros, `js` or `cpp` imports, native dependencies, or asset tooling where verified. |
| **What changes about execution and deployment?** | Describe Haxeon’s runtime, development JIT, native executable, and Wasm host requirements. Map familiar JavaScript, hxcpp, and HashLink workflows to the actual Haxeon equivalents or migration gaps. State what state survives an edit and when a restart is required. |
| **How do I move a project?** | Walk through a small checked-in project. Inventory its dependencies, macros, and platform calls, move a pure module first, adapt the entry point and build configuration, run in the JIT, then build and verify each supported deployment output. Include the original and migrated commands and expected output. |

The brief provides no tested library compatibility results, so these are questions and evidence requirements for the guide. On **About** and **Coming from Haxe**, a concise relationship statement could read: “Haxeon is an independent language and runtime built on Haxe. It compiles a growing subset of Haxe.” Follow that with the versioned compatibility link. On the homepage, lead with the app workflow and label the three outputs as Haxeon’s. Give **Coming from Haxe** a visible entry in Docs so visitors with an existing project can get directly to the migration details.

## 4. Concrete lessons for the Haxeon homepage and docs

1. **Hero — name the language and runtime, then show code and output.** Suggested headline: **“Haxeon is a language and runtime for cross-platform apps.”** Pair a small, real Haxeon snippet with its rendered app output. Use **Start building** as the primary CTA and **See live editing** as the secondary. Haxe’s embedded example gives visitors code they can inspect. Haxeon can bring that evidence into the first screen and connect it to the app they will edit in the next section. [Haxe embedded example](https://try.haxe.org/embed/44ddE)
2. **Apps — make retained state visible.** Use one small app, such as a task list. Let visitors add a task, mark it complete, and type an unsaved draft. Then change a visible label or rendering rule in the code and apply the edit. Show the changed UI with the completed task and draft still present. Use a verified edit in the actual runtime, label what survived, and link to the live-editing reference for restart conditions. HaxeUI’s backend-labelled screenshots and Heaps’ paired source and examples show how much specificity adds to a product claim. [HaxeUI](https://www.haxeui.org/), [Heaps samples](https://heaps.io/samples/)
3. **C/C++ interop — show header → binding → call.** Put the declaration, actual Haxeon binding, and call side by side, with the return value visible. Use a real buildable example that demonstrates what “without a bridge” means in this workflow. Link to the compiler and linker requirements, supported types, and ownership rules. If the example calls a C function, give C++ its own verified example in the docs so readers can see which C++ features the binding supports.
4. **One codebase, three outputs — show what each build produces.** Use the same example for **development in the JIT VM**, **shipping a native AOT executable**, and **building a WebAssembly module**. Give each the actual command, artifact or execution mode, and host requirements. Put supported OSes, architectures, and Wasm environments in a versioned matrix. That answers the practical questions that platform-icon rows leave to setup guides. [Haxe Compiler Targets](https://haxe.org/documentation/introduction/compiler-targets.html), [Lime platform setup](https://lime.openfl.org/docs/home/)
5. **Other uses — keep the examples compact.** Give CLI tools, games and 3D, scripts, and embedding one specific example each, linked to code or a guide where one exists. For games and 3D, show a Haxeon example that runs today. The Haxe ecosystem showcases establish what those projects have shipped and belong in the migration discussion when illustrating existing framework workflows. [HaxeFlixel showcase](https://haxeflixel.com/showcase/), [Heaps showcases](https://heaps.io/about.html)
6. **Start building — get to the first edit quickly.** Structure the default path as **install → run starter app → apply an edit**. Show the expected screen or output after each action. Put native and Wasm setup after that first success and give each its own prerequisites. HaxeFlixel’s three-step guide is a good model for a clear first destination, and OpenFL’s sample command gives readers a concrete installation check. [HaxeFlixel Getting Started](https://haxeflixel.com/documentation/getting-started/), [OpenFL Download](https://www.openfl.org/download/)

For the docs, make **Quickstart**, **Build an app**, **Live editing**, **C/C++ interop**, **Build and deploy**, **Language and API reference**, and **Coming from Haxe** easy to find. Use tutorials for complete tasks, reference pages for rules, and versioned tables for compatibility. Link every homepage example to reproducible source and record the Haxeon version and output it was verified against. Published examples and support tables will communicate progress more directly than a generic news feed.

## 5. Naming, branding, and trademarks

The Haxe Foundation’s **Branding** page publishes approved logo variants and their intended placements, identifies Haxe Orange as `#EA8220`, and asks users to leave the logo free of decorative effects. The Haxe Community terms also address trademarks and logos used in connection with the forum and say use of the site grants no trademark license. I found visual identity guidance and forum terms in the sources checked. I did not find a standalone Foundation naming policy that addresses an independent product name such as **Haxeon**, and this review did not establish trademark availability. [Haxe Foundation Branding](https://haxe.org/foundation/branding.html), [Haxe Community terms, §9](https://community.haxe.org/tos#9-intellectual-property)

Because **Haxeon** starts with the full Haxe name, use a distinct wordmark, icon, palette, favicon, social cards, and docs identity. Keep Haxe references in plain text on About and Coming from Haxe, and state the project’s independence from the Foundation there. Heaps visibly carries Foundation attribution in its footer. Haxeon’s footer, package pages, and repository should identify Haxeon’s own maintainers and support channels. [Heaps footer](https://heaps.io/), [Haxe Foundation](https://haxe.org/foundation/)
