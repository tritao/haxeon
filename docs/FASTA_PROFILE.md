# Fasta hot-loop profile and rejected experiments

Measured on 2026-10-04 after the accepted small-allocation change, using the runtime at fork `2f49c4d4` and
Haxeon `23f64760`. The gate is a repeatable 3% fasta gain, followed by full validation and no regression beyond
noise in the other benchmarks. Both experiments fail the first gate. No compiler/JIT change or new switch is retained.

## Profile

A 25,000,000-input run sampled cpu_core cycles at 1999 Hz with DWARF call chains, pinned to core 0. A first run
identified individual JIT addresses. A second diagnostic run under GDB stops after JIT registration, exports 46
registered function ranges to a perf map, then continues. Report percentages filter to the `hl` process and use
relative sample periods, excluding GDB startup work. These profiles are diagnostic, not acceptance timings.
Kernel symbols are restricted; some native/kernel work remains unresolved. No samples were lost.

| Exclusive sampled category | Share |
|---|---:|
| Fasta.bisect | 33.80% |
| Fasta.randomFasta, including inlined RNG | 33.25% |
| Native Bytes.set | 3.03% |
| utostr | 2.32% |
| hl_from_utf8 | 1.88% |
| uprintf | 1.46% |
| Full allocator | 1.41% |
| Thin allocator | 1.17% |
| hl_utf8_length | 1.17% |

The search and generation loop dominate. Character conversion runs only during code-table initialization.
Bytes.set is a real native call per generated byte, but its own sampled body is much smaller than the search;
this count does not include all caller-side call overhead. Output decoding/formatting and allocation are spread
across several helpers. The RNG's remaining vdivsd is among the hottest individual instructions.

Disassembly shows an indirect method call to bisect for every random character: receiver type and method-table
loads, argument setup, call and return. The inliner resolves the target but excludes its branching loop body
unless explicitly hinted. The search repeatedly loads a Float array element and compares it to the RNG result.
Each Float less-than comparison emits comisd, a parity branch, then the actual condition branch. Array bounds
failure already uses a non-returning cold stub.

## Experiments

1. **Search inlining probe.** A temporary compiler-source overlay allows only Fasta.bisect through the existing
   inliner's branching-body exclusion. Benchmark source is unchanged. This function-specific probe establishes
   whether a general heuristic is worth designing; it is not a proposed production special case. The emitted
   indirect call disappears, but the caller frame grows from 0x38 to 0x48 bytes. The expanded search has a
   stack-carried result phi and additional loads/stores; the saved call is not a net win. Production source was
   never modified for this probe.
2. **Ordered Float comparison probe.** A temporary x86-64 JIT switch, HL_JIT_FLOATCMP=1, reverses the operands
   for < and <= and uses unsigned above/above-or-equal conditions, which are false on unordered inputs. Their
   logical negations include unordered inputs. >= and its negation can use the corresponding direct flags
   without reversal. Equality and inequality keep their original NaN correction. This removes the parity branch
   without changing value definitions or introducing a branch merge. Disassembly confirms comisd xmm0,xmm1
   followed by ja in bisect, replacing the old comisd xmm1,xmm0 / jnp / jb sequence.

The non-power-of-two RNG divisor, 139968, stays a divide. A reciprocal-multiply rewrite would not generally
preserve exact floating-point results; no such rewrite was attempted.

## Timing gate

Core 0, input 2,500,000, nine alternating pairs for each experiment. Both sides use frozen runtimes; the inlining
probe uses two freshly compiled bytecode files from the same scratch compiler, while the JIT probe uses the
same baseline bytecode on both sides. One-minute load stayed <=4 at every accepted pair's recorded observations.
Warmup outputs match. Median peak RSS is approximately 79 MiB, with median changes below 0.05%.

| Experiment | Baseline (s) | Candidate (s) | Improvement | Faster pairs |
|---|---:|---:|---:|---:|
| Inline probability search | 0.449192 | 0.453016 | -0.85% | 1/9 |
| Direct ordered float comparisons | 0.448348 | 0.447571 | +0.17% | 7/9 |

Neither reaches 3%. Search inlining is slower in eight of nine pairs; direct Float comparisons are effectively
flat. Both were discarded. A high profile share does not show that removing one instruction or call will reduce
the critical-path cost of that code.

## Validation and restoration

- At input 1000, baseline and both candidates match the stock Haxe interpreter byte for byte.
- At acceptance input 2,500,000, each candidate's warmup output matches its baseline byte for byte.
- A scratch comparison matrix checks <, <=, >, >=, ==, !=, !(<) and !(>=) over ±0, ±1, ±infinity and NaN.
  Counts from stock Haxe's interpreter are 14, 22, 14, 22, 8, 41, 35, 27. Both Float-comparison switch modes match.
- GDB verifies the intended call removal and comparison-instruction change.
- The JIT file was restored byte for byte and the VM rebuilt. Executable and libhl SHA-256 hashes match the frozen
  accepted runtime exactly. The fork is clean at its tracked commit; no fork commit or submodule bump was needed.
- Full fixture/driver sweeps, Wasm parity, differential, self-hosting, GC/thread stress, DAP and integration suites,
  other-benchmark regression runs, mutation checks and AArch64/32-bit/MSVC runs were not repeated: neither
  experiment passed the first performance gate, and neither is retained. The previous accepted runtime's full
  validation remains recorded in GC_ALLOCATION_PROFILE.md.

Raw profiles, perf maps, disassembly, rejected sources, interpreter references, build logs and all accepted
sample times/loads/RSS/hashes remain under `out/fasta-profile/`. `search-measure.json` and `floatcmp-measure.json`
are the timing records. The committed artifact is this report; benchmark acceptance numbers remain unchanged.
