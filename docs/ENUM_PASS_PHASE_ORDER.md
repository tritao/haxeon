# Enum lowering: phase order and contracts

Status: accepted (dev-71 review 2026-11-11). Implementation follows the separately gated order below; the shared IR model remains owned by dev-c5. This is the enum portion of [ADR 0003 §13](adr/0003-compiler-architecture.md), not a second reachability or provider design. The unified declarations in [the provider model](PROVIDER_REQUESTS.md) remain authoritative: a generated provider has one `IrFunction.kind`, and a pending use is a typed operation in an instruction. There is no separate request list.

## Current order and the ordering problem

In `IrProgramAssembler.assemble`, `IrEnumDynamicDispatch` sees the generated functions and logical declarations before generic owner erasure, value/interface boxes, typed-interface dispatch and checked Dynamic casts. It synthesizes the required enum Dynamic operations and dispatch. Once those helpers exist, `IrEnumRuntimeSpecializations.materialize` adds the concrete enum declarations they require, `IrEnumTagLowering.run` selects nominal scalar tags for eligible payload-free enums and finishes escapes in the functions it rewrites, and `IrInlineEnumLowering.run` classifies and lowers eligible payload-carrying enums. The inline pass can regenerate typed-interface dispatch. Optional scalar/value flow and reflection helpers follow. The assembler builds the final program and calls `IrEnumTagLowering.escapes` over all functions again.

`FrontendCompilation` next runs `IrClosedEnumTagAbi` only for non-live, non-development-metadata builds; then value-array program rewriting, value constructors, value-phi and scalar-argument rewrites, HashLink scalar closures, scalar replacement and nullable scalar flow. It scans enum tag escapes again before inlining and verification. HashLink assembly can generate further scalar-closure adapters and scans again. Wasm closure escape rewriting scans its result, and the Wasm32 linear builder makes closure/interface/cast and varargs adapters, rewrites signature checks and scans yet again before verification. These rescans make correctness depend on where a new helper was inserted. They are not a proof that future generated functions have requested the conversions they need.

## Proposed phase order

1. **Logical input and reachability.** Start from typed functions, declarations, static initializers, native signatures, reflection roots, exported/live entries and the target profile. When ADR 0003 §13's type-aware walker is ready, it follows calls and typed operations to declared providers and prunes once before classification. Until then retain the current conservative roots; this proposal does not introduce a second walker or change live-build roots. A missing provider is an error, not a reason to recover an operation from a name. Dynamic equality and reflection may request a global operation without a statically known enum; the walker intersects those uses with the created/reachable nominal types, rather than discarding them or treating one enum as the global subject. Before the §13 walker exists, preserve the current conservative dispatch set.
2. **Discover specializations and classify representations.** Materialize the nominal enum specializations required by reachable inputs. Compute one immutable decision per nominal enum, using the target and the shared `IrEnumEscapeReach` facts: payload-free tag eligibility, payload-enum inline eligibility, and whether a representation must cross Dynamic, reflection, native, interface, array, closure or live-host boundaries. Preserve the distinct rules: a nominal tag has its own type and checked box/unbox; a payload enum can be inline only under its existing eligibility rules; closed tag ABI selection remains disabled where the current live/development contract requires it. Dynamic/reflective helper requests and the interfaces and native signatures that can affect eligibility must already be represented in these facts; classification cannot assume the absence of a helper that a later stage may introduce. This step reads facts and decides layouts; it does not synthesize helper names or mutate instructions.
3. **Plan typed requests at each producer.** Rewrites that introduce a boundary emit the corresponding typed instruction with its subject and operands. When the tag representation changes an existing `ToDynamic`, cast, call argument/result or stored value into a boundary, the representation rewrite itself emits the operation at that site; it cannot leave an implicit escape for a later scanner to discover. In particular, adapters and closure/cast/varargs generators emit `EnumTagBox(EnumTag(T))` and `EnumTagUnbox(EnumTag(T))` at the exact boundary they create. Array bridges and Dynamic enum operations do likewise for their own boundary. Payload-inline closure adapters currently call `IrInlineEnumEscapes.boxName` and `unboxName`; replace those calls with typed requests whose subject is the logical nominal enum and whose operands/results carry the selected inline storage type. They resolve to the existing `Provider(TypeKey.of(Enum(T)), InlineEnumHelper(box/unbox))` roles. Introduce two typed intrinsic variants, `InlineEnumBox(T)` and `InlineEnumUnbox(T)`, with logical nominal enum `T` and inline storage types on the operands and result. Their verifier rules mirror the corresponding tag operations. This adds no `ProviderOperation` cases: the existing `InlineEnumHelper(box/unbox)` provider operations are keyed by `TypeKey.of(Enum(T))`. Before the model addition lands as its own small first commit, send its diff summary to the lead for dev-c5; follow the same owner review for any other model variant. Each operation carries its type; ordinary call names are linkage only. These operations are the request edges to the providers, not a side record and not an instruction to rescan unrelated functions.
4. **Lower the chosen representations.** Apply nominal tag and payload-inline transformations against the same classification. Materialize needed specializations before changing their users. Preserve exact enum identity, null semantics, constructor payloads, equality/override behavior and interface contracts, and update functions, objects, interfaces, static fields, native signatures and reflection descriptors together. Run the closed-tag ABI decision at its existing semantic boundary before value-array layouts and scalar ABI selection. Rewrites must return unchanged functions when unchanged and retain kind, debug and retention data when replacing them.
5. **Produce and resolve providers.** Gather typed operations from the reachable rewritten functions and from the target-specific adapters as those adapters are constructed. A single provider operation answers each distinct `(subject, operation)` request once, using the declared provider kind and a deterministic collision-safe linkage symbol; it emits the exact-type-check native dependency when required. Resolve operations to the provider call at the last point that still has the required type and target information. The resolution boundary must be explicit for each backend: after its own adapter producers, before that backend's verifier or code generator requires a concrete call. This is demand-driven materialization, not another whole-program `escapes` scan. At each backend resolution boundary, the verifier rejects every unresolved typed enum operation, including an operation introduced by a late producer. During the transition, check mode compares the resolved set at each boundary with the operations a full rescan would find; remove that comparison with the rescans. The verifier also checks arity, types and nominal identity; §13 check mode checks every introduced call is reachable or created by the pass.
6. **Remaining target lowering and checks.** Run value-array rewriting after representation/closed-tag choices and before target scalar argument and closure ABIs; keep the existing constructor, phi, scalar replacement, nullable-flow, inlining and verifier ordering unless a separately reviewed change proves a dependency can move. HashLink, Wasm32 and Wasm GC may have different final adapter-production boundaries, but use the same typed operation and provider contract. Verification stays enabled for each completed stage.

Steps 2–5 describe contracts, not a requirement to build a new pass framework or combine all enum code in one rewrite. Split the migration into independently gated changes: first make every late adapter producer express its escape as the typed operation it needs; then put request resolution at each existing adapter boundary and delete the redundant whole-program rescans; only then consolidate duplicated enum classification and rewrites where their inputs and outputs truly coincide. Do not make the §13 walker a prerequisite for fixing the ordering bug, and do not silently move backend adapters into the frontend.

## Adapter freeze-point review proposal

Dev-71 reviewed this list on 2026-11-12: the HashLink, retained-HashLink, common Wasm and Wasm32 boundaries are approved. The Wasm GC row records the reviewed replacement. Keep each check-mode rescan comparison until its corresponding rescan is deleted; add a test that the inliner preserves already-resolved calls.

| Target and producer | Proposed resolution and verification boundary |
| --- | --- |
| HashLink, including live builds: value-array bridges and factories, then `IrScalarClosures` wrappers and makers and their generated interface-box and checked-cast adapters. Scalar replacement, nullable flow and the inliner follow. | Resolve requests from each producer before the final frontend verifier; establish that the inliner preserves already resolved calls. Plain builds currently verify in `FrontendCompilation` before reachability pruning. Live builds must also reject unresolved operations before lowering: `HlLower.lowerStableMeasured` currently verifies the complete program or the regenerated functions when cached lowering is trusted. |
| HashLink assembly retained for a Wasm compilation: `BackendAssembly` copies the logical program and independently runs `IrScalarClosures`, including its interface and cast rewrites. | Resolve the requests made by that copied assembly's producers before `HlModuleAssembler` lowers it. Its `irVerified` flag is false for a Wasm compilation, so `HlLower.lowerStableMeasured` performs verification; preserve that boundary in both full and cached paths. This is separate from the target Wasm module boundary. |
| Both Wasm targets: `WasmDynamicCalls` generates invocation and varargs helpers after nullable erasure; `WasmScalarClosureEscapes` generates closure, export and restoration wrappers and makers, processes interface-box and checked-cast adapters, and drains missing varargs adapters. GC value-array accessor rewriting precedes these producers. | Resolve their requests before the `IrVerifier.verify` immediately following `WasmScalarClosureEscapes.rewrite` in each module builder. During migration compare these resolved requests with a full rescan in check mode, and reject unresolved typed enum operations at the boundary. |
| Wasm32: `WasmLinearClosureAdapters.generate` adds closure and cast adapters after that first verifier; the builder then rewrites their interface boxes and casts, drains missing varargs adapters, and rewrites signature checks. | Resolve requests from that whole generated batch before the verifier at the current `IrEnumTagLowering.escapes` site, before value-field flattening. Check the post-flattening verifier as well: no later rewrite may introduce an unresolved operation. |
| Wasm GC: `WasmGcClosureAdapters` currently reserves and emits Wasm functions directly; conversions in `WasmGcRepresentation` find enum-tag providers during emission. Scalar ABI rewriting and value-field flattening also clone and rewrite IR functions. | Before migration step 2 reaches GC, change GC closure adapters to IR functions created within the GC module builder, like the Wasm32 adapters. Emit enum box and unbox conversions as typed operations in those functions, resolve them at the builder boundary and pass the same verifier before lowering through `WasmGcRepresentation`. Remove the emission-time `WasmGcContext.enumTagAdapter` lookup. Verify post-ABI and post-flattening IR, including clones, at the lowering boundary. |

The GC adapter migration is a separate gated change after producer migration step 1 and before step 2. Compare generated bytes or demonstrate equal behavior on Wasm GC fixtures with `HAXEON_INLINE=0` and `HAXEON_INLINE=1`. If a specific adapter construct cannot be represented in IR, identify it for dev-71 before choosing a workaround. Do not create a separate request mechanism from signatures: provider requests remain typed operations in instructions under ADR 0003 §13.

## Review questions and evidence

- Before implementing migration step 2, derive and add the per-target freeze points from the code: list every late adapter producer and its resolution boundary for HashLink, Wasm32 and Wasm GC. Send that list to the lead for dev-71 review. A later producer must request and resolve at its own explicit boundary rather than reviving a global scan.
- Confirm `IrEnumEscapeReach` roots and treatment of opaque native handles, reflected maps, inherited interfaces and captured receiver types remain identical; nominally distinct enums must not share a provider merely because they have the same tag values.
- Exercise null and payload cases, Dynamic box/view/unbox and equality, enum tags in arrays, interface and closure adapters, native callbacks, live and plain builds, and both inlining modes on HashLink, Wasm32 and Wasm GC. Check warm versus cold and reuse verification. Compare generated functions and explain any module differences; record timing and allocations where the gates require them.
- Gate each implementation commit with `scripts/gate.sh wave`, including its warm-edit sweep, and the affected fixtures; use `scripts/gate.sh full` and the outer app gates before publishing a code batch. Report existing main-branch red stages separately from new failures.
