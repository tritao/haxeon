# Text formatting

Status: proposal (2026-11-27), not scheduled. How a value becomes text: one interface for text a program shows its users,
one for text a developer reads, both checked by the compiler and written into a formatter. Part of the standard library's
layout ([ADR 0007](../adr/0007-standard-library-layout.md)), whose prelude holds both interfaces.

## Today

Haxeon converts values to text as Haxe does:

- **One runtime printer.** Concatenation with a `String`, interpolation (`'$x'`, which the parser turns into
  concatenation), `trace` and `Std.string` all end in `Std.string(value:Dynamic)`, which on HashLink is the native
  `__std_string`: it reads the value's runtime type and prints it.
- **`toString` by name.** A class with a `toString():String` method prints as what it returns. No interface is checked,
  so a method misspelled or with another signature is not called, silently.
- **Everything else by its shape.** An enum prints as `Case(arguments)`, an anonymous structure as `{a : 1, b : x}`
  (through a generated `__string` method, `IrProgramAssembler.anonymousString`, which reachability keeps only while
  something converts values to strings), a map as `[key => value]`, a class without `toString` as its name.
- **Generated where the compiler knows the type.** A raw-value enum's and a `Flags` enum abstract's `toString` are
  synthesized from their cases (`RawEnumGenerator`, `FlagsGenerator`), never from reflection.

What that costs:

- **One text for two readers.** What a user sees in a label and what a developer sees in a log are the same string, so a
  type either exposes its internals to users or hides them from developers.
- **It runs through `Dynamic`.** Each value is boxed to be printed, the printer is chosen at run time, and the backends
  keep the printers of every type that might be printed.
- **A string per value.** A nested value builds its text, which its container then copies; nothing writes into one
  buffer.
- **Everything prints.** Interpolating a value that has no meaningful text compiles, and shows its structure.

## What other languages do

| Language | Text for users | Text for developers | How it is produced |
|---|---|---|---|
| Rust | `Display`, written by hand: `{}` | `Debug`, derived: `{:?}`, `{:#?}` laid out on lines | written into a `Formatter`; `format!` checked when compiled |
| Swift | `CustomStringConvertible` | `CustomDebugStringConvertible`, else a reflected `Mirror` | interpolation resolves to typed `appendInterpolation` overloads |
| Go | `Stringer`, `%v` | `GoStringer`, `%#v`, else reflection | interfaces satisfied structurally |
| Kotlin, Java, C# | `toString()` on every object | generated for data classes and records; C#'s `[DebuggerDisplay]` | a virtual call; C#'s `IFormattable` takes a format |
| Python | `__str__` | `__repr__` | dynamic |
| Haskell | `Show`, derived | the same | resolved when compiled |

The languages designed most recently agree: two interfaces, the one for users opt-in and the one for developers
everywhere; the printer chosen when compiled; text written into a formatter, not returned; interpolation type-checked.

## Proposal

### `Display`: text for users

```haxe
interface Display {
	function display(out:Formatter):Void;
}
```

- **Written by hand.** A type has text for users only when its author says what it is.
- **What interpolation and concatenation require.** `'$x'` and `"total: " + x` compile when `x` is `Display`; otherwise
  they are a diagnostic that names the type and offers `${x:?}` (below).
- **The core types implement it:** `String` (as it is), `Int`, `Float` (shortest round-trip, Ryu as now), `Bool`,
  `Int64`, and `T?` (its value, or `null`).
- **Generated** for a payload-free enum, a raw-value enum and a `Flags` enum abstract, which print their case names as now.
- **`toString()` is derived from it,** writing into a fresh formatter, for code that needs a `String`.

### `Debug`: text for developers

```haxe
interface Debug {
	function debug(out:Formatter):Void;
}
```

- **Every type has it, generated by the compiler,** as structural equality is (`ValueEqualityGenerator`): a class or
  struct as `Point { x: 1, y: 2 }`, an enum as `Some(3)`, an array as `[1, 2]`, a map as `[a => 1]`, a string quoted
  and escaped (`"a\nb"`), so a log shows what the value is.
- **A type may write its own,** to leave out a field (a cache, a password) or to shorten a large value.
- **What `trace`, assertion failures and the debug interpolation use.** `${x:?}` interpolates `x`'s `Debug` text and
  compiles for every type.
- **Generated only where used.** A type's `debug` is kept when something formats it for debugging, as
  `anonymousString` is kept today, so a release build that never traces a type carries no printer for it.

### `Formatter`

A formatter is where text is written: a buffer the caller owns, so a nested value appends where its container is,
without a string of its own.

```haxe
final class Formatter {
	function write(text:String):Void;
	function writeChar(code:Int):Void;
	function value<T:Display>(value:T):Void;
	function debugValue<T:Debug>(value:T):Void;
	// Helpers for Debug implementations: the generated ones use them, so hand-written ones match.
	function record(name:String):RecordFormatter;   // Point { x: 1, y: 2 }
	function list():ListFormatter;                  // [1, 2]
	function entries():EntriesFormatter;            // [a => 1]
}
```

`${x:#?}` lays a `Debug` value out over lines, one field or element per line; the helpers do the layout, so a
hand-written `Debug` gets it too.

### Cycles

A generated `Debug` of a class prints an object it is already inside as `Point { ... }` instead of recursing, by the
formatter keeping the objects it is in. A value type cannot contain itself, so structs and enums need no such check.

### `Dynamic`

A `Dynamic` value is neither `Display` nor `Debug` when compiled. `std.reflect` keeps a runtime printer for it, as
`Std.string` is today, and `${x:?}` of a `Dynamic` calls that printer.

## Haxe compatibility

`Std.string` and the runtime printer of today move to the compatibility package (ADR 0007, section 9), with Haxe's
conversion rules: concatenation of anything with a `String`, `toString` found by name. Code ported from Haxe keeps
working there; `std` code uses `Display` and `Debug`. A class whose `toString` matches by name can implement `Display`
by writing it, which is what a migration does.

## Stages

1. **`Formatter`, `Display` and `Debug` in the standard library,** with `Display` on the core types and the generated
   enums, and `toString()` derived. Nothing changes for existing code.
2. **The generated `Debug`,** kept where used, and `${x:?}`; `trace` prints `Debug` text.
3. **Interpolation and concatenation require `Display`** in `std` code; the compatibility package keeps Haxe's rule.
4. **The runtime printer leaves the core,** once only the compatibility package and `std.reflect` use it.

## Open questions

- **Format options.** Width, alignment and precision (`${price:.2}`): a format string in the interpolation, as Rust's
  and C#'s, or methods on the formatter (`out.fixed(price, 2)`). The first needs the interpolation to be parsed into
  parts and checked when compiled.
- **Localization.** Whether `Display` takes a locale, as C#'s `IFormattable` does, or text for users that depends on the
  locale is a separate API, leaving `Display` locale-free.
- **The interpolation syntax** for `Debug`: `${x:?}` follows Rust; Haxe's `$x` and `${expr}` forms stay for `Display`.
